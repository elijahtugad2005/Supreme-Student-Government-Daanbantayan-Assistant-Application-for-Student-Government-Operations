The SSG Office Assistant Application implements a multi-tier, client-side authorization pipeline architected around the principles of Zero-Trust Security and Defense-in-Depth. Protecting sensitive institutional modules (such as financial disbursements, Death Aid remittances, student inventories, and administrative records) requires an airtight mechanism that intercepts every navigation attempt before component mounting occurs.

1. Initial Trigger & Identity Hydration Layer (AuthContext)

When a user triggers client-side navigation (e.g., browsing to /finance, /admin, or /documents), the top-level ProtectedRoute component intercepts the React Router lifecycle. Access evaluation begins by querying the singleton AuthContext:

  • currentUser: Represents the verified Firebase User object. If null, the user is classified as a guest (isGuest = true).
  • userRole & Custom Claims: Decoded from the signed Firebase ID Token, establishing the baseline role (e.g., admin, finance_secretary, secretary, governor, representative).
  • userPermissions & Overrides: A reactive dictionary reflecting Firestore-backed per-user permission overrides. This allows system administrators to grant or revoke granular capabilities without redefining role definitions.

2. The Four-Tier ProtectedRoute Evaluation Pipeline

The ProtectedRoute component executes four rigorous validation gates before granting component access:

  • Check 1 (Authentication Gate): Evaluates isGuest && !allowGuest. If an unauthenticated user attempts to access an internal route, navigation immediately diverts to Path B-2 (<Navigate to="/login" replace />). The original target path is preserved via React Router's location.state to facilitate seamless post-authentication routing. Conversely, if allowGuest === true (e.g., Public Catalog or Track Order), execution returns children directly.
  • Check 2 (Route-Level Matrix Validation): Invokes canAccessRoute(user, pathname). This checks the attempted route against the canonical route permissions table (defined in permissions.js). If the user's role is not registered as a valid occupant of the path, the pipeline short-circuits to Path B-1 with a route mismatch audit message.
  • Check 3 & 4 (Role & Granular Permission Catalog): Performs multi-criteria capability evaluation:
    • Super-Admin Bypass: If user.role === 'admin', full access is granted immediately.
    • Role Conformance: Asserts that allowedRoles.length === 0 || allowedRoles.includes(userRole).
    • Granular Permissions: When requiredPermissions are specified, hasPermission(user, key) verifies that individual access overrides or role defaults satisfy either every() or some() constraints (controlled by the anyPermission prop).

3. Decision Outcomes & System Integrity Protection

  • Path A (Authorized Mounting): If all gates pass, ProtectedRoute returns children. The target component (e.g., FinanceDashboard, UserManagement, InventoryManagement) mounts cleanly, initiating secure backend data queries.
  • Path B (Unauthorized Isolation): If any check fails, component mounting is completely blocked. Rather than crashing or leaking unrendered child state, the system renders either the custom customAccessDenied node or the default AccessDenied component (displaying an audit timestamp, the user's current role, and the specific missing capabilities).

This architecture ensures that client-side components containing proprietary student information or financial ledgers never execute their internal useEffect or API data-fetching hooks unless the cryptographic and role parameters are verified.
